# The Four Tests, and the Five Outcomes

Building has to survive all four tests. Failing any one produces a non-build
outcome, and four of the five outcomes are not "build."

Run the tests in this order. The order matters: coverage before recurrence
wastes the researcher's time describing work that something already does,
and the judgment-load test placed last arrives after everyone has already
decided to build.

## Test 1: Recurrence

**Has this happened before, and will it happen enough more times to repay
the build?**

Ask for instances, not for a description. "How many times have you done this
already, and when was the last one?" A researcher who can name three
specific occasions has a pattern. A researcher who says "constantly" and
cannot name two has a feeling, which may still be right but is not yet
evidence.

Working default: **three past instances, or a credible five still to come.**
This is a default rather than a rule, it has no evidence behind it, and the
researcher can move it. Say so rather than presenting it as a finding.

Below the threshold, the outcome is *not yet*. Name the threshold and say
what would change the answer, so the researcher can come back when it does.

## Test 2: Stability

**Has the procedure settled?**

The question that surfaces this: "if you did it again tomorrow, would you do
it the same way?" Then: "and did you do it the same way the last two times?"

Work still finding its shape cannot be encoded. An instrument built over an
unsettled procedure is wrong by its third use, and worse, it freezes a
procedure the researcher was still improving. Unstable work that recurs is a
candidate for a written checklist, not for code.

The trap: fieldwork procedures often look stable to the person doing them and
turn out to vary by site, by participant, or by what the day allowed. Ask for
the last two instances specifically rather than for the general case.

## Test 3: Coverage

**Does something already do this?**

Search before proposing. The library ships skills across the research
lifecycle, a set of Colab notebooks, and MCP tools for data collection,
chunking, codebook generation, coding, thematic analysis, and reading
marked-up documents. Finding the thing that already exists is a better
outcome than building, and it is the most common one.

Search properly rather than from memory of the catalog: the skill list, the
notebook catalog through `list_notebooks`, and the tool list through
`toolkit_info`. Then look outside the toolkit. A standard command line
utility, an existing package, or a feature of software the researcher already
runs are all legitimate answers and are usually cheaper than anything built.

If something covers most of it, say which part is covered and how much is
left. A gap of ten percent is rarely worth an instrument.

## Test 4: Judgment Load

**Does this repeat because every instance needs a fresh interpretive call?**

This is the test that makes the question anthropological rather than generic,
and it is the one most often skipped because by this point everybody wants to
build something.

Some work repeats because it is mechanical and nobody automated it. Other
work repeats because each instance is a separate act of interpretation that
happens to have the same shape. Coding a transcript, deciding what a field
note means, judging whether two participants' accounts describe the same
event, deciding what a photograph shows: these look like batch operations and
are not. The repetition is the work.

Diagnostic question: "when you did this the last three times, did you ever
reach a different answer on something that looked the same?" A yes means
judgment is live in the loop. A confident no is worth one more probe, because
the answer is often no right up until it matters.

Where judgment is live, the honest outcome is *leave it manual*, or build
something that prepares the material and stops short of the call. Preparing,
sorting, and presenting are legitimate; deciding is not.

## The five outcomes

**1. Already exists.** Name it, and show how to reach it. Do not paraphrase
what it does; point at it.

**2. Change the procedure.** The work repeats because of how it is organized,
not because it needs an instrument. Files named inconsistently, a step done
in the wrong order, four tools where one would do. This outcome costs nothing
and is under-proposed.

**3. Leave it manual.** It repeats because the judgment is the point. Say
which part is the judgment, and offer to build something that prepares the
material if there is preparation worth doing.

**4. Not yet.** Below the recurrence threshold or the procedure has not
settled. Name what would change the answer.

**5. Build.** All four tests passed. Hand to the tool-building skill, and
carry the recurrence evidence with it: the instances, what varies between
them, what is mechanical, and what the researcher has to decide each time.
That is most of the opening material for a specification, and it is wasted if
it stays in this conversation.

## When someone is pushing for outcome 5

A researcher who wants to build something can usually produce answers that
pass any test. The check that survives this: **ask what would have to be true
for the answer to flip.** Someone who has actually tested their case can name
it. Someone who has decided in advance cannot, and that is worth saying once,
plainly, before proceeding to build with them anyway if they still want to.

The decision is theirs. The gate exists to make it a decision rather than an
enthusiasm.
