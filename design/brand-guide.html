01 — Foundation
Brand Overview
One small set of tokens and components for every screen the toolkit shows, from a ratification desk inside a chat to an exported decision record.
Brand Positioning

The toolkit asks researchers to decide things the model has drafted: codes, rulings, themes. The interface exists to make those decisions clear, quick and on the record, and to never let a model draft pass for a decision.

Brand Principles
  • Show who decided. Model drafts sit in a dashed model box; the researcher's decisions are solid.
  • What needs you is the loudest thing on screen. One open decision at a time, raised, with the yellow Needs-you status.
  • One next step, numbered. One primary button per view; a disabled button says why.
Brand Descriptors

Plain · Exact · Accountable · Calm

Color Rules
action means you can do this — Primary buttons, selected choices, links and the current stage. Text on it is on-action.
attention is only the Needs-you status — and the current segment of Progress. It is the loudest colour in the system and is never decoration.
done, refusal and model keep one meaning each — done is recorded results, refusal is errors and server refusals with a sentence, model is what the model wrote that nobody has decided.
Code colours are marks, never text — code-1 to code-6 colour dots, lines and nodes. A code keeps the same tone everywhere; past six, repeat with the name shown.
line is decorative only — Control borders use line-strong, which meets 3:1. focus is an alias of action.

08 — Components
Component Patterns
Fifteen components cover every screen. Their markup, React versions and previews live in design/system/components/.
ComponentWhat it is for
ButtonThree kinds: primary for the one thing the view is for, secondary for everything else, quiet for small moves like Change or Go to next.
BylineThe credit every toolkit view carries: the toolkit, its author, the version, and where to cite it.
ChoiceGroupA question with its answers as pills you tap (rounded tiles when an answer has a description); checkboxes when several can apply, radios when one can.
CodeTagA code's name with its colour dot, used wherever a code is named outside a choice.
DecisionCardOne decision the researcher has to make: a code to ratify, a disagreement to rule on, a theme to confirm.
NoticeWhat the server said, in a sentence: a refusal that names what to fix, a confirmation, or information.
PassageA participant's words, set large in the serif so they never read as interface text and are the first thing the eye lands on.

ProvenanceShows who wrote something: a dashed box for the model's draft that nobody has decided, a solid box for the researcher's decision.
StagesThe stages of a longer task, in order, with where you are and how much is left in each.
StatusA word plus a mark that says where something stands; colour is never the only signal.
StepA numbered instruction that makes the order of clicks visible: 1 choose, 2 record.
TableRows of records: the decision log, counts per code, job results.
TallyHow many decisions are left, with the way to the next one and the action that finishes the stage.

13 — Voice
Voice & Tone
Plain words for a researcher who is deciding something that matters.
Voice Attributes
  • Plain: plain words, sentence case, no exclamation marks.
  • Exact: numbers are counted from the record, such as 208 of 212 chunks, never most.
  • Accountable: the interface says who decided. The model is the model; the researcher is you.
  • Faithful: participants are quoted exactly, never tidied, trimmed or paraphrased.
Writing Style
  • Labels are verbs plus objects: Record ruling, Ratify codebook, Review the record.
  • Questions end in a question mark: Which codes apply to this passage?
  • Refusals say what was refused and exactly what is missing: Can't ratify yet. 2 codes have no decision. No apologies, no something went wrong.
  • Call machine output the model. Don't call it AI, assistant or Claude in the interface.
  • A disabled button always says why, beside it.
Tone by Context
Context Tone Example
A decision inside a chatDirect and brief; one question at a time.Which codes apply to this passage?
A refusal from the serverFactual; names what is missing.Can't ratify yet. 2 codes have no decision: Being watched, Permits and city rules.
An exported decision recordFormal and complete; fit for a methods appendix.Ratified by the researcher on 12 March: 6 codes, 2 revised, 1 merged.
14 — Usage
Usage Guidelines
The rules most often broken.

Do

  • Show one open decision at a time, with Progress above it.
  • Put what the model wrote in a dashed model box until someone decides.
  • Number the clicks inside a decision with Step: 1 choose, 2 record.
  • End every view with the Byline.
  • Pair every status colour with a word and a mark.

Don't

  • Restyle a model draft as solid because it was accepted.
  • Use attention, done or refusal for decoration.
  • Set code colours as text.
  • Add a logo or mark beside the Byline, or reword it.
  • Put more than one primary button in a view.
